# Examples

## `rag-assistant`

An internal assistant that answers questions from a knowledge base and can open support tickets. The feature directory `specs/001-rag-assistant/` shows what ThreatSpec produces from a bare `spec.md` **before any plan exists**:

| File | Produced by | What to look at |
|---|---|---|
| `spec.md` | `/speckit.specify`, then the model command's render | The managed `### Security Requirements` block (SR-001 … SR-016) between the `threatspec` markers, inserted before Success Criteria; nothing else was touched |
| `threat-model.yaml` | `/speckit.threatspec.model` (first pass, profiles `stride`, `llm`, `agent`) | 3 actors, 3 trust zones, 6 assets, 3 components, 5 data flows, 15 surfaces, 14 dispositions with reasons, 19 rated threats plus 4 `needs-clarification` questions, 16 mitigations, 16 requirements with Given/When/Then acceptance |
| `threat-model.md` | `threatspec.sh render` | The human view: summary, Mermaid data-flow diagram, threat table with edition-pinned OWASP and ATLAS mappings |
| `security/check-report.md` | `threatspec.sh check --persist` | Four C12 findings (the open questions) and one aggregated C6 line; nothing HIGH or CRITICAL |
| `security/coverage.md` | `threatspec.sh coverage` | Every profile technique with its state; one technique is `uncovered`, which is exactly what the check command's S2 pass is for |

The model was generated by a coding agent executing the installed `speckit.threatspec.model` skill with no prior context, then passed through the engine unchanged apart from the feature id. It is a realistic first pass, not a curated ideal: the check command's semantic passes still find things to improve (an unmeasurable SR-001, a disposition that should be a clarification, a duplicate threat), and that is the point of the workflow.

### Reproduce

```bash
specify init demo --integration claude && cd demo
specify extension add --dev /path/to/spec-kit-threatspec
mkdir -p specs/001-rag-assistant && cp /path/to/spec-kit-threatspec/examples/rag-assistant/specs/001-rag-assistant/spec.md specs/001-rag-assistant/
export SPECIFY_FEATURE=001-rag-assistant
# in your agent:
/speckit.threatspec.model
/speckit.threatspec.check
```

Or run only the deterministic engine on the shipped files:

```bash
python3 scripts/python/threatspec.py --repo . --feature-dir examples/rag-assistant/specs/001-rag-assistant check
python3 scripts/python/threatspec.py --repo . --feature-dir examples/rag-assistant/specs/001-rag-assistant coverage
```

### Next steps in the lifecycle (not included here)

`/speckit.clarify` to answer the four open questions, `/speckit.plan`, then `/speckit.threatspec.model --from-plan` to attach threats to concrete components and replace the component-id touchpoints with file paths, `/speckit.tasks`, and after implementation `/speckit.threatspec.converge`. The test fixture under `tests/fixtures/rag-assistant/` shows a smaller model further along that path, with tasks, touchpoint files, and a convergence run.
